How the secondhand brand system is built

Every rule is written once, in plain words. Then it is held three ways: a script that fails a render, a line a fresh judge is handed, or Ben’s own eye. The same rules run on the app, the website, a deck, a post and a story. Only one table of numbers changes between them.

The whole thing on one page

Read it top to bottom. Each layer only takes from the one above it, so a change starts where it belongs and flows down. The dashed line is how the system learns.

Each file, what it does and why it is that way

FileWhat it doesWhy it is built this way
product/words.mdEvery product call by Ben or Nate, quoted word for word, append only.A rule cites the quote it rests on, so nobody argues from memory and nothing Ben said gets paraphrased into something else.
brand/ledger.mdPicks Ben locked (L), means agents decided (A), and questions still open (R).Taste is Ben’s. Agents can propose, never lock. A locked pick with no rule row fails the repo check.
brand/constitution.mdPart I the ends. Part II thirteen articles (codes, color, type, space, imagery, voice). Part III each medium. Part IV the check list. Part V how the file changes.Written as law: one reading per line. A word like “subtle” or “usually” with no number beside it fails the vague-words check in Articles 4 to 10 and Part III.
.agents/ui-rules.jsonOne row per rule: is it a script, a judge line, Ben’s eye, or a lesson seen once.So a rule is never only prose. A lesson seen twice fails until it becomes a check or a judge line. A Part IV “Script” row must point at a real check with a failing test.
.agents/ui-states.jsonThe states every screen, job and control must be drawn in (new, empty, one, typical, dense, loading, failed, offline), and extreme content to stuff into every slot.Mocks only show the happy path. This list grows from what broke: one command adds a case, and every later check runs it.
brand/tokens.cssEvery color, size, space, corner, weight, gradient and part size, in light and dark.The only place a value lives. The app gets it through a generated TypeScript file, and the checker reads it, so a value changes everywhere in one edit.
brand/media.json → media.cssPer medium: canvas, margins, text sizes, the unit that scales space and corners, wordmark place, word limit, layouts.The only thing that differs between media. A test fails if it disagrees with the Part III table; media.css is generated so a deck never types a raw number.
brand/templates/A deck, a post and a story built from named layouts. Copy one and change the words and photos.A maker agent working from rules alone guessed wrong four times. Starting from a file that already passes removes the guessing. A test keeps all three passing.
scripts/brand-check.mjsOpens any HTML in Chromium at the medium’s size, in light and dark, and measures every element and line of text.Rules about looks are only checkable on a render. It collects facts and judges nothing, so the rules stay separate and testable.
.agents/checks/render.mjsThe rules, as pure functions over those facts: fonts, sizes, weights, color as ground, contrast on real pixels, margins, one field, part sizes, corners, states, layouts, color blind distance.Every message names the rule and its article, so the fix is obvious. Each rule has a test that shows it failing on what it exists to catch.
.agents/check.mjsRuns before every push and in CI: files agree, no secrets, no drift, every test passes.So nothing depends on an agent remembering to look.
scripts/ui-rules.mjs judgePrints the judge lines for one medium, each starting “Fail if”.A fresh agent with no context judges what a script cannot see, such as whether a headline makes one point. It gets only the lines, never the whole rulebook.
Skills: ui-screen, writing, image-genThe order to work in: read, build from parts and tokens, run the checks, hand the render to a judge, show Ben.Skills say when to do things. Values and rules stay in their own files, so a skill never holds a second copy.

One rule, from a sentence to a failing screen

1 · words

Ben: “everything should be standardized size wise no matter whats in it”. Quoted in words.md.

2 · decision

Locked as L37 in the ledger: things of a similar size are one width and height.

3 · rule

Part IV row B31 says how it is measured. ui-rules.json says a script holds it: render:B31.

4 · value

tokens.css sets --card-decision-h: 156px.

5 · output

A mock marks its card data-part="card-decision" and a long title stretches it to 178 px.

6 · check

brand-check fails it: “is 178 px tall: a [card-decision] is --card-decision-h, 156 px”. The edge state that broke it was already on the list.

What stays the same everywhere

  • Parts I and II of the constitution: the codes, color, type, space, voice and the ten rules for communicating in any medium.
  • Every token: the same eight hues, the same two faces, the same corners and spacing scale.
  • Every check in render.mjs runs on every medium. It reads the medium’s row and adjusts its numbers, not its logic.
  • Judge lines with no medium named apply to screens; the rest name the media they apply to.

What changes per medium

  • One row in media.json: canvas, margins, sizes, the unit (1 on screens, 2 on a deck, 3 on a post), word limit, wordmark place, layouts.
  • One section in Part III: what the reader is doing there, and the lines specific to it.
  • One template in brand/templates/.
  • Judge lines tagged with that medium.

Adding something new, like a poster or an email

1

Add a column to the Part III table and a row to media.json with the same numbers. A test fails until they agree.

2

Run node scripts/media-css.mjs. The new medium gets its variables.

3

Write its Part III section, one reading per line. The vague-words check holds you to it.

4

Build a template from the named layouts and add it to the template test. Every existing rule already runs on it.

Why it will not drift

  • Each value lives in one file. Copies are generated, and a check fails if a generated file is stale.
  • The Part III table and media.json are compared on every push.
  • Every locked pick needs a row saying who holds it, and every “Script” row needs a real check with a failing test.
  • A commit that fixes a screen and teaches the system nothing gets a warning asking what was learned.
  • CI runs all of it in a real browser, so a green build means the rules ran on renders.

What it cannot do yet

  • The font files are not in the repo, so CI measures in a fallback face and only warns. A render on a machine with the fonts is the real test.
  • An audit agent wrote 63 pages built to break a rule and still pass. The checker catches 42; the 21 it misses (text in pseudo-elements, timers, iframes and the like) are listed in brand/explore/system-audit/.
  • App screens are checked as HTML mocks and web renders, not on the device.
  • A pass means the rules were followed, not that it looks good. The judge and Ben still look.
