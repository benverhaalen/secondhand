### Refactor

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. Large or cross-cutting structural work needs its own auditable plan. This playbook is the focused-to-medium change.

1. Pin the behavior contract first. Learn how the affected subsystem works to find the contract, then write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin. Break the code on purpose once to confirm the pin catches a change. Run `step start refactor --prove "<the pin command>"`, and `step lock` the pin's baseline files if someone else (or an earlier stage) wrote them.
2. Name the structure the code is missing per `references/principles/model-the-domain.md`. Boring code stays when the shape is already clear and local. The reshape must delete branches or invalid states, not add indirection.
3. Name the target shape. State what the module layout, types, and call graph should be if built today (`references/principles/foundational-thinking.md`, `references/principles/redesign-from-first-principles.md`). If the target crosses a function boundary, sketch competing types, signatures, and module structures in parallel before the move.
4. Subtract before you add. Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape (`references/principles/subtract-before-you-add.md`). The smallest change that reaches the target shape ships (`references/principles/laziness-protocol.md`). A speculative cleanup that "might help" gets reverted.
5. Move in small behavior-preserving steps, each keeping the pin green. For API reshapes, migrate every caller and delete the old API in the same wave (`references/principles/migrate-callers-then-delete-legacy-apis.md`). No compatibility shims, no parallel old-and-new paths. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. If you hand the mechanical edits to `builder` (per the size rule), give it a specific scope (file paths, the names being moved, the behavior to hold, and the principle files it must read: references/principles/subtract-before-you-add.md, references/principles/laziness-protocol.md, references/principles/migrate-callers-then-delete-legacy-apis.md, references/principles/prove-it-works.md).
6. Prove behavior is unchanged on the real artifact, not "it compiles" (`references/principles/prove-it-works.md`). For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface by driving the real CLI, TUI, or UI. Say whether the result is provably the same or "trust me".
7. Confirm the change is worth keeping. The success measure is reduced reader load (`references/principles/minimize-reader-load.md`). If the diff does not lower reader load somewhere, revert it.
8. When the owner asks for a commit or PR, rebase into small ordered commits. A subtraction commit, then the reshape, then any follow-on cleanup. Shape them with `references/principles/sequence-verifiable-units.md`, so each behavior-preserving slice stays green before the next. Run the `clean` skill before saying done.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof (provably the same or "trust me"), the reader-load delta, what shipped and what got reverted. No new behavior.
