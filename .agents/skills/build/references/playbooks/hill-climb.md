### Hill-climb

**You own the metric and the experiment's integrity. Supervise and review.** For sustained, iterative improvement of one measurable thing against a target. A one-off fix is Bug fix or a single measured perf fix. This is the loop.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection (`references/principles/prove-it-works.md`). Never delete features or tests, or skip tests, to move the number.

1. Ground the workload and architecture before choosing the metric. Learn how the target works, name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts so a lucky early win can't end the run (the example "at least 50% better than baseline and at least 10 iterations" is this shape). Use the user's numbers when given, otherwise agree them.
2. Build the measurement harness, prove its sensitivity, then freeze it (`references/principles/build-the-lever.md`). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. Vet the harness's limiter, errors, repeatability, relevance, and whether the work happened before you freeze it, and make it print its error count and a count of the work done (`references/principles/explain-the-number.md`). Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (median of N, not a single run). Lock it and its baseline with `step lock` so no attempt can edit them. Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change. Run `step start hill-climb --prove "<regression gate command>"`.
3. Open a local decision log. A `decision.tsv`, one row per attempt: id, hypothesis, change, before, after, delta, tests, verdict (kept or reverted), note. Read it before each attempt. Keep it out of the tree (gitignored).
4. Ground each hypothesis in the architecture model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses: don't do it, don't do it again, do it less, later, when they're not looking, concurrently, cheaper.
5. Loop, one hypothesis per iteration:
   - Make the change yourself, or hand it to `builder` per the size rule with a tight scope and the principle files it must read: references/principles/prove-it-works.md, references/principles/laziness-protocol.md, references/principles/sequence-verifiable-units.md. Supervise and review the diff rather than typing it when a helper does it (`references/principles/guard-the-context-window.md`). When several independent hypotheses are live, fan them to parallel builders, each in its own worktree, only after `overlap add` finds their files do not overlap (`references/principles/separate-before-serializing-shared-state.md`).
   - Measure before and after with the frozen harness, and run the regression gate.
   - Accept only when the metric moves past noise and the gate stays green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - When the owner asks for commits, one commit per accepted fix, staging only the files you changed (`git add <files>`, never `-A`). Log the row either way, kept or reverted.
   Each iteration ends in a check before the next begins (`references/principles/sequence-verifiable-units.md`).
6. Push past the first plateau. On a stall, several rejects in a row, pivot category, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number (`references/principles/laziness-protocol.md`).
7. Stop when the predicate is met, or when the remaining ideas are marginal and not worth their cost. Don't relax the predicate to meet it, and don't quit while cheap untried hypotheses remain. If you are stuck, surface it instead of spinning: `step end --state blocked --reason "..."`.
8. Run the `clean` skill before saying done. When the owner asks for a PR, stack the accepted commits in the order they landed. If the project now has the event log and this frozen measuring command, make the self-improving-loop offer in `references/every-playbook.md`, once.

**Reply:** the metric and target, baseline to final with the percent delta, iterations run (kept vs reverted), each accepted fix on one line, the `decision.tsv` path, and the best idea you would try next if pushed further.
