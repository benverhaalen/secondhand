# The hosted browser pool: how it operates

`createPool({launcher, profileRoot, accounts, vault, address, maxAccounts, publicConcurrency, leases, log})` in `pool.ts`.

- **Browsers are browser-use browsers, reached over CDP** (`cdp.ts`, Nate: "use browser-use"). `cdpLauncher(pw, localChrome({executablePath, scratch}))` is a local Chrome on a kept profile directory, with its debugging port bound to 127.0.0.1. `cdpLauncher(pw, browserUseCloud({apiKey}))` is a Browser Use Cloud browser (`POST /api/v4/browsers`, connect to `cdpUrl`, `PATCH {action:"stop"}` on close; the key goes only in the `X-Browser-Use-API-Key` header), chosen by `sourceFromEnv()` when `BROWSER_USE_API_KEY` is present (local Chrome otherwise). `playwrightLauncher` (`playwright.ts`) stays as the plain local fallback.
- **Sign-in is storage state behind `account.token_ref`** (`auth.ts`): `{cookies, origins[].localStorage}`, the shape browser-use's `export_storage_state` writes. It loads into the account's browser when its first lease starts and is exported back to the vault when every lease ends. It lives only in the secret scope (the `AuthVault` port), never in a repo file, a log or a trace. Close sends `Browser.close` and waits for Chrome to exit, so the profile's cookie store is flushed.
- **Headed where the site needs it.** `PROFILES[site].headed` (platform.ts) is true for Depop and Mercari, which refuse a headless browser (runs/bp-1.md, run 2). Their accounts, and public reads that pass `site`, run in a real window, on a virtual display on a server. Every other site runs headless.
- **Linked accounts only.** An account task runs only when `accounts.byId` finds an account row with stored sign-in state; otherwise it answers `not_linked` with nothing launched. `warmLinked(person_id)` warms exactly the person's linked accounts. Public market reads need no link.

- **One profile per account.** Each linked account has its own directory under `profileRoot`, launched as a Playwright persistent context, which is one browser process per account. It has its own steady address from `address(account_id)`. The directory is a credential: it never leaves the host and never goes in a log or a backup we do not encrypt.
- **Warm.** `warm(account_ids)` launches the profiles ahead of any call. A dispatch then only opens a page: about 60 ms against 0.3 to 1.7 s cold (runs/bp-1.md).
- **At once, in parallel.** `dispatchAll(tasks)` sends every task immediately, each on its own page. Linked accounts run side by side. Public reads share up to `publicConcurrency` anonymous contexts and queue past that.
- **One job per account.** A second job on a leased account gets 409 at once, so steps never interleave. Pass the shared events Leases port to the pool, sign-in, hand-off, poster and scheduler. `withLease` renews the account lease through the whole operation; nested pool calls inherit it and leave its release to the outer operation. The pool also permits only one active page per account.
- **New sign-in.** `invalidate(account_id)` closes and evicts that account’s idle context. Sign-in and hand-off call it before replacing vault state. AuthVault `snapshot` returns state with a version; `compareAndPut` atomically refuses exports from an older version, including after deletion. Production vault adapters must implement both operations atomically.
- **Restart.** If a profile's browser dies, the next dispatch relaunches the same directory, so the login survives. A site that logged us out answers `auth_expired` in its adapter.
- **Memory cap.** Past `maxAccounts` the least recently used idle profile is closed and stays on disk. A leased one is never closed.
- **Never.** No code here solves a CAPTCHA or defeats a challenge (no `captcha_solver`): a challenge pauses the session, and the person clears it in the live browser (`live_url` on a cloud browser), then the job resumes. No forged fingerprint of our own.

| verb | how the pool serves it |
|---|---|
| `read_listings`, `read_inbox`, `read_offers`, `read_orders`, `read_stats` | a page in the account's warm profile, under the account's lease |
| `search` | an anonymous public context, many at once; the cookie runner or a plain request first where recon found an endpoint |
| `post`, `revise`, `end`, `relist`, `send_message`, `answer_offer`, `make_offer`, `save` | a page in the account's warm profile; the lease is held through the read-back; never replayed |

## Cloud profile sessions

For new cloud accounts, use `storeProfileRegistry(store)` from `auth.ts` (`memoryProfileRegistry()` in tests). It stores profile references in the existing `account` table, with `id = account_id`, owner-scoped reads and writes, and no sign-in material. Its rows carry `account_id`, `user_id`, `site`, `profile_id`, `state`, `linked_at`, `last_ok_at` and `data`; Store adds `id` and `version`. Existing account rows without a profile require explicit migration: the registry refuses them before creating a vendor profile, so it cannot discard legacy account configuration.

Compose `browserUseCloud({apiKey, profileFor: registryProfileFor(registry), onStopFailed})`, then `cdpLauncher<SessionPage>(pw, source)` and `createPool({launcher, registry, profileRoot, leases, log})`. Pass the same registry, launcher, pool, profileRoot, leases and log to `sessionClient`, plus `ttlMs` and two vendor ports: `createProfile({user_id, account_id, site}): Promise<string>` and `deleteProfile(profile_id): Promise<void>`. Creation must return a fresh profile id; deletion must reject on failure. The registry's `hasProfile(profile_id)` checks references across all account rows before cleanup. Neither vendor response nor error text is logged.

`clientFor(site, {user_id, account_id})` supplies the existing Poshmark, Mercari and Depop `Client`, or eBay `PageClient`. Every read checks ownership and link state and takes the account lease. A busy pool returns status 429 to the adapter, which reports `rate_limited` with `retry_after`; cancellation throws `AbortError`. No site installs request interception. With a registry, `warm` and `warmLinked` skip account profiles because those legacy methods lack an owner; scoped dispatch launches them. Public warming is unchanged. Cloud contexts expose no storage import/export; local Chrome retains the legacy behavior above.

`startLink(site, owner)` requires an existing, owned profile-registry row before calling the vendor. It keeps the new profile in memory and passes its id as `LaunchOptions.pending_profile_id` to the launcher. This is an internal launch option, never a caller-supplied account field. The old row and warm browser remain intact. An authenticated server viewer route redeems `liveView(user_id, handle)` once; never log or cache its URL.

`finishLink(user_id, handle)` consumes the handle, reads the adapter's inbox, stops the browser and checks `profileSaved()`. Poshmark, Mercari and Depop currently return only message rows, with no owner or account evidence. Completion therefore returns `no_route` with `handoff`, even for a populated 200 response, and leaves the stored row unchanged. Publication remains disabled until an adapter returns positive evidence of the signed-in account. eBay linking returns `no_route`: its page adapter has no account verification read and `PROFILES.ebay.login` is null. Existing linked profiles still serve reads; eBay account-level reads require its OAuth `Client`.

Failed setup or verification, cancellation and expiry stop the pending browser and delete its unpublished profile. Cleanup releases the account lease before attempting deletion and never deletes a profile referenced by an account row. Failed deletion records a fixed error and the profile id; it never records the vendor error. Wire `onStopFailed` to the existing browser cleanup owner. Handles and pending profiles live only in process memory; the supplied Store persists published registry rows. Process-crash recovery of pending vendor profiles is not implemented.

The runtime is not composed here. No adapter or parser was changed. Signed-in fixtures remain synthetic; no live sign-in or read verification was run.
