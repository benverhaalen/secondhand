## Five things found in the repo that a judge would hit first

These are defects, not ideas. Each one is in the ranked table below.

1. **Delete does not delete.** `core.observation` is created with `delta.appendOnly = true` ([01_tables.sql](../../../databricks/sql/01_tables.sql) line 28), and append-only tables "don't allow deleting existing records" (*observed*, [table properties](https://docs.databricks.com/aws/en/delta/table-properties)). [purge.py](../../../deploy/tasks/purge.py) runs `delete from` on every table with a `user_id`, so it would fail on `observation`. It also points at `workspace.secondhand` (the bundle default in [databricks.yml](../../../deploy/databricks.yml) line 14), while the tables live in `secondhand.core`. And a `DELETE` alone leaves the rows readable by time travel: Databricks' own guide says deletion vectors need `REORG TABLE ... APPLY (PURGE)` and old files need `VACUUM` (*observed*, [GDPR and CCPA with Delta](https://docs.databricks.com/aws/en/security/privacy/gdpr-delta)).
2. **Two `param` tables.** [fit.py](../../../jobs/valuation/fit.py) lines 28 to 29 and 77 write `workspace.secondhand.param`; [01_tables.sql](../../../databricks/sql/01_tables.sql) defines `secondhand.core.param`, which the loader fills and the dashboard is meant to read. [data-use.md](../../data-use.md) line 76 puts live params in Lakebase with history in Delta. Three answers for one table.
3. **The parity pair `scopeKey` disagrees today.** TS writes `kind=apparel|site=depop|segment=|state=|person=usr_nate` ([param.ts](../../../app/src/engines/param/param.ts) line 36); Python writes sorted JSON, `{"kind": "apparel", ...}` ([registry.py](../../../jobs/param/registry.py) line 26). A `core.param.scope` written by one side is never found by the other. [databricks-build.md §5](../../databricks-build.md#5-parity-each-calculation-once-in-two-languages-checked) lists this pair first; it will fail.
4. **The loader works around its own row filter.** [load.mjs](../../../databricks/load/load.mjs) maps the workspace principal to `usr_ben` for the duration of the load and deletes the mapping in `finally`. If the process dies between those lines, Nate's principal can read Ben's mirror rows. The platform answer is an exempt writer identity (row 5). The same file commits a personal email address as `PRINCIPAL` (line 19), which the repo's git rules forbid; read it from the environment or `current_user()`.
5. **No MLflow anywhere.** `grep -ri mlflow jobs/` returns nothing (*observed*). [databricks-build.md §4 and §6](../../databricks-build.md#4-the-pipeline-and-the-jobs) promise one MLflow run per backtest and per param move. A Databricks judge opens the Experiments page first.

## The five-minute path for Databricks judges

1. **Catalog Explorer, `secondhand`** (40 s): the schemas, the comments on every table, the entity diagram from the keys (row 4), the ABAC policies on the catalog and the tags (row 5), the Lineage tab from `raw.landing` to `core.citation`.
2. **One number, down to its rows** (60 s): `SELECT * FROM measures.why(...)` on a shown price: the observations, their pages and hashes, their rights, `equal = true`. Then a hidden one: `too_few`, with its count. Then the `CHECK` refusing a shown number without a citation.
3. **Genie** (60 s): a thick question answered as a verified answer through `why()`; a thin one answered with its count; the benchmark tab, n of N.
4. **The weights** (60 s): the Experiments page for `param_walk`: one run per month on real StockX sales, a promotion, a refused challenger and a rollback; the model's `@champion` alias history; `table_changes('secondhand.core.param', 0)`.
5. **The guardrails side by side** (40 s): the table from row 8, `block_hallucination` and `claim_check` on the same 50 drafts, and one decision's trace end to end.
6. **The dashboard** (20 s): the five tiles, plus spend by usage policy.

**Must be real by then, not example data:** `market.comp` from the StockX 2019 rows ([jobs/valuation/data/README.md](../../../jobs/valuation/data/README.md)); the backtest and walk results; the recompute check; the Genie benchmark scores; the guardrail comparison. The `decision`, `claim_check` and `storefront_snapshot` rows may stay fixture-driven if every tile that shows them says "fixture", which [load.mjs](../../../databricks/load/load.mjs) already records in `source` and `payload.mode`.

**What they will ask that we cannot answer yet:**
- "Your users are not workspace users. What does the row filter protect?" Today it protects analysts and judges in the workspace; the app's users are protected by Lakebase or Postgres RLS on `app.user_id` ([databricks.md §5.3](../../databricks.md#a-lakebase-pattern-for-consumer-apps)). Say that, and show the two-users-one-pool test once it runs.
- "Delete me. Is it gone from time travel?" Not until row 1 lands, and then only after the VACUUM window.
- "Why not the model registry for params?" Answer with row 6: the registry holds the model-sized ones; per-scope scalars are rows because thousands of tiny models per scope is the wrong tool (*inferred*).
- "What does your claim check catch that ours does not?" Only row 8's numbers answer this.
- "What does one item cost?" `system.billing.usage` by usage policy (row 9); no number exists yet.
- "Is this Free Edition?" The two spec pages disagree (question 1).

## What is already right and should not be touched

- One catalog, one owner, schemas by purpose, a comment on every table and column ([01_tables.sql](../../../databricks/sql/01_tables.sql)).
- Rights as columns on each row and `comp_for_model` as the only table a fit reads ([databricks-build.md §3](../../databricks-build.md#3-layout-and-lineage)): this is the one governance idea the platform does not have.
