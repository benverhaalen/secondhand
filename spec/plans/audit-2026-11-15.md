## 1. The ten things that matter

1. **The phone app is not connected to the server.** There is no API client, no server address setting and no token storage in the app. 26 of 28 screens draw `app/src/demo` data; sign-in, linking a site, an offer, a post, a label and a message are timers over local state (*observed*).
2. **Nobody can sign in.** The server's email sign-in creates a code and sends it nowhere: the sender composed in `app/src/edge/auth.ts` is an empty function. Apple and Google verifiers exist, and Apple sign-in is dropped for now. So every route that needs a person is unreachable by a real person today (*observed*: 401 on the dev server).
3. **A signed-out search works, from two sources.** On the dev server a search for "levis 501 jeans" settled in 3.2 s: Poshmark 48 found, Dupe 40 found. Depop, Mercari, eBay and Facebook each ended `failed` with `no_route`, because the runtime is composed with no options: the anonymous browser clients, the Apify lane and the eBay page client are built, tested and proved live outside the server, and never handed to it (*observed*).
4. **Routes do not share memory, and one case of it was fixed while this audit ran.** At 11:42 UTC the job a search started could not be read back by the next request (404, *observed*). The cause was one job store per route; the app-wiring lead fixed that case at 11:47 UTC (87252eeb, the job store shared across routes), and a retest at 11:46 with the data folder set read the job and its stream back (*observed*; that retest ran on a working tree that may already have held the fix, so it does not show the data folder was what mattered). Every other store is still one per route (section 10, the server).
5. **The price a person gets is for the example item.** `POST /v1/valuations` prices the spec's example item whatever id is sent, with a fixed condition, floor and parameter version, and reads sold comps only when a variable names the site (*observed*, `app/src/edge/api/valuations.ts:14`).
6. **The learning loop is built and not joined.** Gathering more evidence, weighing stored comps, citing rows and learning from an outcome each exist with tests; the proof script finds one link of ten working and seven "built, not called". Nothing a search reads is stored anywhere (*observed*).
7. **Many signed-in routes serve the contract's example data.** Orders, insights, scores, follows, genie, records, products and trends answer for the one example user or with fixed example JSON; conversations cannot send; the assist route's model port throws (*observed*, section 3).
8. **Capture is a rehearsal.** The camera takes a real photo and discards it; judging is a timer over demo facts; the server's capture routes hand out example upload addresses; there is no native module, so LiDAR is a flag in demo data (*observed*).
9. **Databricks is beside the product, not under it.** The served app touches the workspace in one place, the health route. The dashboard, Genie space, governance and backtests are real in the bundle; the fits job is paused; nothing the app reads flows in and nothing fitted flows back (*observed* in code; the workspace itself was not queried for this audit).
10. **There is no website on main.** No `web/`, no host configuration (*not found*). One draft exists off main: a Next.js front for the buying conversation, about 45 files with fixtures and tests, committed on the Mac branch `w/buy-web-1` at 11:50 UTC and judged by nobody (*observed* by file listing; not built or run for this audit).

What is solid: the site harness and its adapters (a wide tested surface), the route wrapper's identity and error handling, the event pipeline's tests, the valuation arithmetic under test, the Databricks bundle's 304 passing tests, and a gate that runs 3,300 tests in about 90 seconds.

## 3. The server

**What a request is.** Every route file under `app/src/app/v1/` (76 files) wraps a handler in `app/src/edge/api/` with one function that reads the bearer token or a visitor id, strips any `user_id` a client sends, applies a rate limit and an idempotency key, and shapes errors (`app/src/edge/api/http.ts:104`). That wrapper is sound and tested.

**What is composed.** `export const runtime = createRuntime(store)` passes no options (`app/src/edge/api/runtime.ts:311`). So:

| Piece | Built and tested | Given to the running server |
|---|---|---|
| Anonymous cloud-browser clients for eBay and Depop (`harness/public-client.ts`) | yes, proved live | no |
| The signed-in client and profile registry (`harness/session-client.ts`) | yes, 130 tests | no |
| The Apify lane (`harness/sites/apify/`) | yes | no |
| Databricks and Genie clients | yes | the health route only |
| The notifier | yes | no |
| The watcher and the event pipeline | yes | built, and nothing starts a tick |
| The buying conversation loop and its tools | landed today as drafts | no: the assist route's model port throws |

**State.** The Store is in memory unless `SECONDHAND_DATA_DIR` is set, then one JSON file rewritten on every write. Sign-in sessions, email codes, rate limits, idempotency keys, capture rows, follows, job event frames and the decision signing key live in module memory and are lost on a restart (*observed*, about thirty maps listed in the backend evidence).

**Routes by what they really do** (*observed* in each handler):

| State | Routes |
|---|---|
| Real, and scoped to the person | items (read, patch, strategy), rules, limits, wants, me, today, decisions, events, jobs, conversations (read and receive) |
| Real, works signed out | search, jobs for a visitor, out |
| Real, but needs something not composed | valuations (the person's item, live sold reads), accounts import (live reads), me delete (the workspace purge port), auth by email (a sender), captures (uploads, the judging jobs) |
| Example data, or only the example user | orders and its labels, ship, handed-over and pick-list; appointments; insights and goals; scores, basis and ranker; experiments; follows; genie; records; index, products, history and trends; compare; item listings, sell and attributes |
| Throws or cannot finish | assist (no model), conversations send, draft and answer-offer (no transport) |

**Isolation.** Reads go through the Store scoped by person. The lookups that take an id alone are the system accounts lookup the watcher uses, two in `browser/auth.ts`, and the job read, which checks the owner one step later; a seeded example job is readable by any visitor (*observed*, each marked as a shortcut in the code).

## 4. Search and the sources

- **Path.** `POST /v1/search` validates, starts a job, runs all sources at once and returns 202 with a stream address. Each source ends as arrived, late or failed with a code, and its counts (found, used, dropped by reason) are appended as frames. The response shape is honest: a source that cannot answer says why.
- **As composed, signed out:** Dupe and Poshmark answer by plain requests. Depop and eBay need the anonymous browser clients. Facebook needs the Apify lane. Mercari needs a linked account and a local Chrome. A visitor is treated as a person, so all six rows are asked and four fail on every search.
- **Proved outside the server today** ([the run](../../research/cross-cutting/nate/runs/public-client-live.md)): eBay through the anonymous client, 240 listings of 15 to 17 fields in about 5 s over 32 reads with one timeout; Depop, 24 rows in 1 to 2 s, 32 of 32. The eBay read still waits about twice as long as the page needs.
- **Nothing read is kept.** A search writes its job and nothing else: no observation rows, no rights fields in the Store (they exist on adapter rows and in the Databricks SQL).
- **Product identity is not resolved.** The search sets `product: null`; the same-product reconcile runs only inside a search and needs a model key.

## 5. Valuation and the engines

- **Served.** `engines/valuation/check.ts` runs D1 to D15 (comps weighting, effective sample, fees and keep) on whatever comps arrive, capped at 10 s. No calibration and no sale curve are passed, so the range's state is "not checked yet" and the chance of sale, days and price path are null.
- **Not served.** `intel/gather.ts`, `intel/learn.ts` and `intel/classify.ts` are imported only by the proof script. Appraise, the marketing calculations, the conformal interval declarations, the person model, several trust rules and the negotiation outcome row have no caller in a served path.
- **Offline only.** The brand-premium measure (A11) and the attribute record (AD9) are Python under `jobs/measures/`, run by hand. The other adaptation measures (A1 to A10, most of AD1 to AD12, MI3 to MI6, C1 to C6) could not be matched to code id for id (*not found*).
- **Parked, not on main.** `w/eng-valuation-2` (an improved valuation, 4 commits), `w/eng-ad9-1` (the attribute record in TypeScript), `w/int-obs-1` (the observation store, 4 commits), `w/int-byid-2` (account lookups scoped by person), `w/cap-parts-1` (parts of an item).
- **Benchmark.** `bench/` compares the product with one plain Poshmark request per item. The runs recorded in its README, all today, range from 0 of 20 to 20 of 20 answered as the wiring changed; the latest shows 2 sources an answer. No rival is coded.

## 10. Faults the expert reviewers found

Each review read the code as it stands and quoted a line for every finding; the ones marked *checked* were reread by the orchestrator at the cited line.

### Databricks, the jobs and the data

Verdict: fix before the nightly fits are switched back on. Not read by this review: SQL files 03, 05, 06, 07 and 10, the dashboard and Genie definitions, the loaders and `bench/`.

1. **A fit would write its parameters to the wrong place.** `jobs/valuation/fit.py` builds its registry table from the schema it is given, and the bundle gives the fits the market schema (`deploy/databricks.yml:56`), so a first promotion creates an ungoverned `market.param` while the governed registry is `core.param`. Fix: parameters always go to `core`; comps are read from the market schema.
2. **A fit reads rows it may not model on** (*checked*). `fit.py:35` reads the bare `comp` table, and the `comp_for_model` view filters on `may_model = true` alone, not the scope, so a shown-only row could enter a served parameter. Fix: every job that writes a parameter reads a view that checks both, with a test that no bare `comp` appears in its SQL.
3. **A purge can record "done" with rows left.** The break-glass grant is keyed by principal with no lease (`databricks/break_glass.py`); if the guard job and a purge run as the same principal one can remove the other's grant, the purge's deletes then match nothing under the row filter, and its count check reads zero through the same filter (`deploy/tasks/purge.py:74`). Fix: confirm the grant still exists before counting, and give each grant an id.
4. **The alert can hide a guard that never ran.** `deploy/resources/alerts.yml` has no subscriptions and treats an empty result as OK. `databricks/sql/14_engine.sql:37` carries the market model's figures as literals.
5. **A shown-only row has no home.** Neither the observation table nor the evidence table has a per-row `use_scope`, so "Apify rows are shown and never modelled on" cannot be stored as ruled.
6. **The failing Python tests, by cause.** Two are stale tests (`databricks/test_guard.py:165` counts statements wrongly; `deploy/tasks/test_purge.py:44` expects an older insert order). One is real drift: the Python parameter row lacks four fields the TypeScript registry has (`origin`, `previous_version`, `keep`, `days_since_last`). The measures tests need the repo root on the import path in `jobs/conftest.py`; the studio tests need to skip when `cv2` is absent.

The shortest path to the product using the lakehouse for real, in the reviewer's words: the server writes what a search reads as JSON lines to a landing volume, one bundle job loads them, and the fitted parameters are exported back to the server on a timer. The warehouse is never queried while a person waits. Dupe's rows are refused in the writer.

### Search, the harness and the browser

Not read in depth by this review: the signed-in client, the link flow, reconcile and the browser pool. It ran no tests.

1. **The composition gap, and what closes it** (*checked* on the dev server). `createRuntime(store)` must be given the anonymous clients, built from the cloud-browser key or a local Chrome; then Depop and eBay answer signed out. Poshmark and Dupe need nothing. Mercari has no signed-out lane. Facebook needs the Apify token. The local Chrome path is read under two different variable names (`browser/cdp.ts:146` and `api/runtime.ts:132`).
2. **Dupe's rows are stored, against Dupe's condition** (*checked*: about 80 Dupe rows in the store file after two searches on the dev server; the file was deleted). A finished job keeps its rows in the Store and nothing prunes the Store row, so with the data folder set, which is the only setting in which the server works, every search writes them to disk. The same path would keep Apify rows past `keep_until`.
3. **Wiring the Apify token as the code stands would break two rulings** (*checked*, `api/search.ts:249`). Every caller is treated as a person, so a visitor reaches the person-only Facebook row; the eBay fallback puts Apify in the path an answer waits on; shown-only rows are handed to the same-product model; and the spend cap is in process memory against a visitor id a client can rotate. Dormant today only because no token is composed.
4. **A visitor is told Mercari has no route when the truth is "needs your account"** (*checked*, `intel/public/search.ts:55` runs before the account test at `:56`).
5. **The settled answer can stall, and a late read is never cancelled.** The settle timer starts only after every source has started while each deadline starts at its own slot (`intel/run.ts:171`, `:129`), so a queued eBay read with its 10 s pace gap outlasts the budget; a timed-out read keeps its lane because the shared abort is never fired (`intel/run.ts:76`).
6. **One person's read is not shared with the next.** Reads are scoped per person (`api/search.ts:170`), so N visitors asking the same thing cost N browser reads in a row.
7. **One throw outside the per-source catch fails the whole job** (`api/search.ts:213`), and a source that lands late is dropped without a frame (`:148`).
8. **The counts are not yet honest enough for a screen that shows them.** `unavailable_or_duplicate` merges three reasons; unreadable cards are left out of the found count; listings not in dollars skip the price cap and sort after the rest (`api/search.ts:87`, `:66`, `:37`).
9. **An empty query is accepted** (`api/search.ts:243`).
10. **Turning Depop "live" by the variable would call Depop's own web data address from the server** (`api/runtime.ts:100`), which is the private-endpoint question Nate allowed only from the site's own page. Search through the anonymous browser client is a page read and is clean.

For eBay's speed the reviewer's order is: measure first, keep the browser warm, ask for fewer rows for the first answer (240 a page is about 4 MB), merge the two in-page evaluations, share one read across visitors, and move the 5 s second-host pause off the answer's path.

Solid and to be left alone: the single-flight read and its cache, the judge and the back-off on a challenge, the shape check with its parse fallback, one lane per site, the source filter, and the Apify run reservation.

### The server: runtime, sign-in, isolation and state

Verdict: fix the first three before anyone is hosted on it. The review ran no tests and did not read the capture handler, the watcher or the pipeline.

1. **Each route is its own program, so nothing is shared between routes** (*checked* in part: `app/src/edge/api/jobs.ts:166` already carries a note of the same fault and shares the job store through `globalThis`; nothing else does). The exported server loads every route file as a separate bundle with its own copy of every module; the dev server evaluates a bundle fresh for each request. So a session created by the sign-in route does not exist for any other route: every signed-in route answers 401 in a production build (`app/src/edge/auth.ts:249`, `app/src/edge/api/http.ts:50`).
2. **With the data folder set, routes overwrite each other's rows.** Each bundle loads the store file once and rewrites the whole file from its own memory (`app/src/edge/events/file-store.ts:41`, `:44`), so one route's write deletes what another route wrote since, and each serves stale reads.
3. **No sign-in code is ever sent** (*checked*, `app/src/edge/auth.ts:247`).
4. **The watcher, the pipeline and the job claims never run**: the runtime returns `runOnce` and nothing calls it (`app/src/edge/api/runtime.ts:301`).
5. **About forty routes answer only for the example user**, including the item list, orders, follows, insights and conversations (`app/src/edge/api/captures.ts:78`), and example rows are seeded into the real store at start (`runtime.ts:72`).
6. **Acting on a decision fails** without a signing key set, because each bundle makes its own random key (`app/src/edge/api/decisions.ts:21`).
7. **A visitor id is chosen by the client**: whoever holds another visitor's id reads their jobs, and the rate limit resets by changing the header unless the peer-address variable is set (`http.ts:131`).
8. **Two identical requests at once both run**: the idempotency slot is stored only after the handler returns (`http.ts:139`).
9. **A replayed refresh token does not revoke its family**, and asking for a new code spends a verify attempt (`auth.ts:221`, `:213`).
10. **Push tokens are stored raw** (`app/src/edge/api/me.ts:67`), and deleting an account stays paused because no workspace is composed (`me.ts:43`).

The fix the reviewer recommends for 1, 2 and 4 together: one Node server entry that imports every handler once, so there is one store, one sign-in state, one vault and one key; a real database file on the machine's disk; the ticks started at boot; one machine; and a refusal to start when a required variable is missing.

Solid and to be left alone: the route wrapper's stripping of a client's `user_id` and its error shape, the sign-in primitives, the ownership checks in the harness, the versioning in `me.ts`, and the file store's validation.

### The engines and the buying conversation

Verdict: the arithmetic is mostly sound and the served path is not connected to it. Not read: trust, score, the negotiation chooser, `intel/learn.ts` and `classify.ts`. No tests were run.

1. **The served valuation throws away fresh comps.** It prices the example item and passes the example's date as "now" (`app/src/edge/api/valuations.ts:21`); `engines/valuation/comps.ts:95` drops any comp dated after that, so live sold comps newer than the fixture are lost.
2. **The calibration widens the range wrongly.** A log-ratio value is applied as one symmetric number of cents (`engines/valuation/aci.ts:131`, `check.ts:52`): for a range of $20 to $60 it widens $21 a side and the low end goes negative, where the right form gives about $5 below and $21 above. The parked valuation branch already has the fix.
3. **"Checked" can never be reached.** Coverage is hard-coded to zero and failing (`aci.ts:133`); after forgetting, a quantile saturates at the top score (`aci.ts:117`); whole-dollar rounding can make the low end zero and then the range function throws, losing the learning event (`comps.ts:248`, `aci.ts:56`).
4. **Why the thin-basis note never shows** (the proof's link 1). The proof defaults a basis level that the sold reader never produces, and the check never calls the guard (`engines/proof/proof.ts:115`); cited ids resolve to no stored rows (`check.ts:48`).
5. **Two calls can disagree about one price.** The conversation's tool decides what is visible from a second comps call, separate from the check that produced the money shown (`app/src/edge/assist/tools.ts:277`). The keep calculation has an unsourced tax rate and no sale date, so the stale-fee flag never fires.
6. **The conversation's tools are real and safely validated; its loop is not yet bounded.** No cost cap (six rounds of 16,000 tokens, parallel tools, web search always on), text streamed before the number gate runs, the gate matching by value and not by row, a raw vendor error reaching the person, and a default caller of "visitor" that makes the sold tools answer "not connected". The evaluation runner does not match the loop's shape, so no live run can work, and its 25 questions check tool choice and phrasing, not figures against rows.

Parked branches: both merge cleanly. The improved valuation should merge after a gate run on the merged tree, and is still not served, because nothing calls `valuate`, the calibration carries no counts, the observation port has no implementation, the warm band's median is invented from the ends, and one site's citation can throw and fail the whole check. The other-brand branch is additive and matches the rulings, and nothing sets the fields that would make it run.

### The phone app and capture

Verdict: sound as a design shell; a phone build cannot reach a server. On this machine the type check passes or fails with the generated route types, which are git-ignored.

1. **No client, address or token store**, and the two existing fetches are relative, so they fail on a phone (`app/src/app/dev/health.tsx:9`, `want.tsx:55`).
2. **Crash uploads go to `/api/log`**, a path the server does not serve (`log/crash.js:39`).
3. **Capture discards its work**: the photo is dropped, taken with a setting that skips the orientation fix (`app/src/app/camera.tsx:131`), judging is a timer (`:135`), library picks are dropped (`:158`), LiDAR is a flag in the address (`:73`).
4. **Three links lead nowhere**, hidden by type casts: `(tabs)/index.tsx:283`, `(tabs)/sell.tsx:243`, `messages/index.tsx:112`; `camera.tsx:261` can route to an item with no id.
5. **Fold state resets on a phone** (`(tabs)/sell.tsx:41` uses browser storage). No not-found page, no per-route error boundary, no virtualized list anywhere.
6. **Development screens ship in a release**, the log's build label is fixed to "dev", one screen says "Downloaded" when nothing was, and a file-system package is imported without being declared.

For a first internal build the project lacks the development client its profile needs, an address per profile, a privacy manifest and the secure-store package. For measuring: ARKit scene depth first, Object Capture second for rigid goods, RoomPlan not at all.
